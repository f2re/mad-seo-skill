# От реального затруднения к статье

## Один рабочий проход

| Этап | Исполнитель | Вход → результат | Условие перехода |
|---|---|---|---|
| 1. Границы | Координатор | Запрос → ниша и цель | Проблема относится к устройствам MAD-auto |
| 2. Поиск | Исследователь проблем | search-plan → прочитанные обсуждения | URL, дата события, попытка решения; без личных данных |
| 3. Сопоставление | Инженер решения | Проблема + документация → возможность | Нет подмены рекламным обещанием |
| 4. Разбор спроса | Аналитик | Сигналы/выгрузки → приоритет | Неизвестные метрики остаются неизвестными |
| 5. Поиск дубля | Поисковый редактор | Карта URL → new/update/merge | Одно намерение — одна основная страница |
| 6. Задание | Координатор | brief + область применимости | Понятна новая польза относительно инструкции |
| 7. Доказательства | Проверяющий факты | Источники → связанные утверждения | Прочитаны первичные технические источники |
| 8. Черновик | Автор | claims → pack | Нет выдуманного опыта, замеров и совместимости |
| 9. Иллюстрации | Арт-директор | Шаги → снимки или схема | Реальный интерфейс; подписи; права; скрыты личные данные |
| 10. Технический разбор | Инженер/безопасность | Версии, шаги, ограничения → замечания | Высокий риск требует человека-инженера |
| 11. Редактура | Редактор | Черновик → предметный текст | Каждый абзац даёт действие, объяснение или ограничение |
| 12. Поиск и ИИ | Поисковый редактор | Статья → метаданные и ссылки | Разметка соответствует видимому тексту |
| 13. Автопроверка | CLI | validate → ошибки/предупреждения | Ошибок нет; это ещё не подтверждение истинности |
| 14. Приёмка | Человек | preview + review → конкретный хеш | Проверены все разделы и предупреждения |
| 15. Экспорт | Координатор | export --approved → пакет CMS | Только локальные файлы, без отправки |
| 16. Измерение | Аналитик | Реальные выгрузки → корректировка | Изменения правил и статьи снова проверяются |

Это стадии, не 16 обязательных вызовов модели. Небольшой материал не требует отдельного агента
на каждый шаг. Исследование проблем и проверку возможностей можно проводить параллельно;
текст пишется только после их сопоставления. Автор и приёмщик не должны быть одной ролью в одном проходе.

## Файлы задания

`content/jobs/<slug>/brief.json` хранит вопрос, ссылки на признаки спроса, возможности решения,
область применимости, ограничения, риск и целевой URL. `sources.json` содержит URL, раздел,
дату чтения и SHA256 сохранённой разрешённой выдержки. `claims.json` связывает технические
утверждения с первоисточниками. `pack.json` — заголовок, резюме, разделы, изображения и авторство.
`evidence/` — разрешённые выдержки или собственные фактологические заметки, не полные зеркала чужих сайтов.

## Делегирование

Передайте проверяющему цель, пути, нужные источники и критерий отказа. Запишите реально использованную
среду и имя роли. Отчёт: `verdict: pass/revise/blocked`, `findings[]` с путём/разделом,
`source_urls[]`, `not_checked[]`, `required_changes[]`. Проверяющий не изменяет текст и не выдаёт себя за человека.
После двух неудачных циклов материал получает `blocked`; координатор собирает один список недостающих фактов.

## Два уровня применимости

`general`: статья объясняет документированный принцип, не обещает совместимость конкретной машины.
Экспорт сам выводит заметное предупреждение о непроверенной связке версий.
`exact`: обязательны ЭБУ, его ПО, адаптер, прошивка адаптера, приложение, версия и платформа.
Замеры и утверждения точной совместимости должны содержать ту же область применимости в `claims`.
Неизвестная версия не заполняется по сходству названия. `documented` не превращается в `tested`.

## Версия и утверждение

SHA256 охватывает текст, источники и их файлы, изображения, конфигурацию, базу знаний, инструкции,
код и образцы голоса. Изменение любого из них делает утверждение неактуальным. Рецензия также
хешируется. Это локальный контроль версии, не удостоверение личности и не криптографическая подпись инженера.
